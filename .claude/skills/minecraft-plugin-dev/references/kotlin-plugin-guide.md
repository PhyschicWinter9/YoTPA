# Kotlin Delta for Paper/Spigot/Folia Plugins

> Read this **alongside** `paper-api-guide.md`, not instead of it — the Paper API surface is identical in Kotlin. This file only covers what genuinely differs: project setup, runtime/shading concerns, null-safety interop, coroutine patterns, and idiom notes. Verified against official Kotlin docs, JSpecify docs, and community Paper+Kotlin tooling in mid-August 2026 (Paper version numbers below refreshed 2026-09-17 — see `SKILL.md`'s Current Version Snapshot for what's current at read time).

## 1. The one thing that trips people up: the server has no Kotlin runtime

Paper/Spigot servers ship a JVM and the Paper API — they do **not** bundle `kotlin-stdlib`. If you don't shade it into your plugin jar, your plugin crashes on load with `NoClassDefFoundError` the moment it touches any Kotlin-generated bytecode (which is immediately — even a bare `class Foo : JavaPlugin()` needs Kotlin intrinsics). This is the single most common Kotlin-plugin mistake; always shade the stdlib unless the user tells you another plugin already provides it on their server (rare, and fragile to rely on).

## 2. Gradle setup

```kotlin
plugins {
    id("java")
    kotlin("jvm") version "2.2.20" // check kotlinlang.org for the current stable release
    id("com.gradleup.shadow") version "8.3.5"
}

group = "io.github.yourname"
version = "1.0.0"

repositories {
    mavenCentral()
    maven("https://repo.papermc.io/repository/maven-public/")
}

dependencies {
    // 26.2 shown as the stable baseline as of writing — check SKILL.md's version snapshot first
    compileOnly("io.papermc.paper:paper-api:26.2.build.+")
    implementation(kotlin("stdlib")) // gets shaded in — see below
}

kotlin {
    jvmToolchain(25)
}

tasks {
    shadowJar {
        // relocate kotlin stdlib only if you're worried about clashing with
        // another Kotlin plugin on the same server; usually not necessary
        archiveClassifier.set("")
    }
    build { dependsOn(shadowJar) }
}
```

Note `implementation(kotlin("stdlib"))`, not `compileOnly` — unlike the Paper API, the Kotlin runtime is *not* provided by the server, so it must end up in the shaded jar. Everything else about the build (Paper repository, `paper-plugin.yml` vs `plugin.yml`, Java 25 toolchain) is unchanged from the Java setup in the main reference.

IntelliJ's **Minecraft Development** plugin project wizard supports Kotlin project scaffolding directly if you'd rather not hand-write the Gradle file.

## 3. Main class

```kotlin
package io.github.yourname.exampleplugin

import org.bukkit.plugin.java.JavaPlugin

class ExamplePlugin : JavaPlugin() {

    override fun onEnable() {
        logger.info("ExamplePlugin has been enabled!")
        saveDefaultConfig()
        server.pluginManager.registerEvents(JoinListener(), this)
    }

    override fun onDisable() {
        logger.info("ExamplePlugin has been disabled!")
    }

    companion object {
        lateinit var instance: ExamplePlugin
            private set
    }

    init {
        instance = this
    }
}
```

The `companion object` + `instance` pattern is the idiomatic Kotlin replacement for the common Java pattern of a static `getPlugin(ExamplePlugin.class)` accessor — it gives other classes in your plugin a typed singleton reference without threading `JavaPlugin` through every constructor. Keep it `private set` so nothing outside the class can reassign it.

`main:` in `plugin.yml`/`paper-plugin.yml` still points at the same fully-qualified class name — Kotlin classes compile to ordinary JVM classes, so nothing about the descriptor changes.

## 4. Null-safety interop with the Paper API (worth knowing about)

Paper's API is progressively being annotated with **JSpecify** (`org.jspecify.annotations.NullMarked` / `@Nullable`) rather than older JetBrains-only annotations — this is visible directly in Paper's source (e.g. `com.destroystokyo.paper.SkinParts` and other newer/updated classes carry `@NullMarked`). Kotlin's compiler has first-class, built-in support for JSpecify annotations: a `@NullMarked` Java type shows up in Kotlin as genuinely non-null (not a `String!` platform type), and an explicit `@Nullable` return shows up as a real `String?`. Where a Paper class *is* JSpecify-annotated, the Kotlin compiler will actually stop you at compile time from misusing it — which is a real improvement over the old "everything from Java is a platform type, cross your fingers" situation.

Practically:
- Don't reflexively add `!!` to every Paper API call — check whether the type already resolved to a proper `String`/`Component`/etc. (non-nullable) rather than `String!`. If it's a real nullable (`?`), handle it with `?.` or an explicit null check instead of force-unwrapping.
- Not all of the Paper API is JSpecify-annotated yet — older, untouched corners of the Bukkit-inherited API will still show up as unmarked platform types in Kotlin. Treat those defensively (as if nullable) unless you've confirmed otherwise, same as you would in Java.
- If in doubt, hover the type in IntelliJ (or check the Javadoc at `jd.papermc.io`) rather than guessing.

## 5. Coroutines, and why Folia makes this less trivial than usual

Kotlin coroutines are a natural fit for the async-heavy parts of plugin code (DB calls, HTTP), but plain `kotlinx-coroutines-core` has no idea what a Bukkit/Paper "thread" even is — you need a scheduler-aware dispatcher, and if you might ever run on Folia, a *region-aware* one, because (per the main reference, §19) Folia has no single main thread.

**Option A — manual dispatcher (no extra dependency).** Wrap the region-aware schedulers from the main reference in a small `CoroutineDispatcher`:

```kotlin
import kotlinx.coroutines.*
import org.bukkit.Bukkit
import org.bukkit.plugin.Plugin
import kotlin.coroutines.CoroutineContext

class RegionDispatcher(private val plugin: Plugin, private val location: org.bukkit.Location) : CoroutineDispatcher() {
    override fun dispatch(context: CoroutineContext, block: Runnable) {
        Bukkit.getRegionScheduler().run(plugin, location) { block.run() }
    }
}

class AsyncDispatcher(private val plugin: Plugin) : CoroutineDispatcher() {
    override fun dispatch(context: CoroutineContext, block: Runnable) {
        Bukkit.getAsyncScheduler().runNow(plugin) { block.run() }
    }
}
```

```kotlin
fun healPlayer(player: Player) = plugin.launch(AsyncDispatcher(plugin)) {
    val coins = database.fetchCoins(player.uniqueId) // suspends off-thread
    withContext(RegionDispatcher(plugin, player.location)) {
        player.health = player.getAttribute(Attribute.MAX_HEALTH)!!.value // back on the right thread
    }
}
```

**Option B — a maintained library.** [MCCoroutine](https://github.com/shynixn/MCCoroutine) is a widely-used library purpose-built for this: it gives you `suspend fun` event handlers and commands directly (`suspend fun onPlayerJoinEvent(event: PlayerJoinEvent)` with `@EventHandler`), and on Folia specifically exposes five dispatchers — `mainDispatcher`, `globalRegionDispatcher`, `regionDispatcher(location)`, `entityDispatcher(entity)`, and `asyncDispatcher` — falling back transparently to the plain Bukkit scheduler when not running on Folia. For any plugin doing non-trivial async work, prefer this over hand-rolling dispatchers.

**The rule that doesn't change**: whichever approach you use, the same discipline from the main reference applies — never touch region/entity/game state from a dispatcher that isn't currently on the right thread for that data. Coroutines make it easy to *write* code that looks sequential; they don't make it safe to skip the thread-ownership rules.

## 6. Idiom notes

- **Listeners**: Bukkit's `registerEvents` needs a `Listener` instance with `@EventHandler`-annotated methods — you can't register a bare lambda as an event handler (the annotation-based reflection lookup requires a real method). Keep listeners as ordinary classes implementing `Listener`.
- **Trailing lambdas** read nicely for scheduler calls: `Bukkit.getAsyncScheduler().runNow(plugin) { /* work */ }` instead of the Java `task -> { ... }` form.
- **Data classes** are a good fit for simple config/DTO-style objects (e.g. a `data class HomeLocation(val world: String, val x: Double, val y: Double, val z: Double)`), but avoid them for anything Bukkit's `ConfigurationSerializable` needs to round-trip unless you implement that interface explicitly — data class `copy()`/`equals()` generation doesn't substitute for it.
- **Extension functions** are a nice way to keep MiniMessage/Component conversions terse across a codebase, e.g. `fun String.mm(): Component = MiniMessage.miniMessage().deserialize(this)` — but keep them in one obvious file so they're easy to find, not scattered.
- **Avoid `lateinit var` for anything that isn't guaranteed to be set in `onEnable()`/`init` before use** — it trades a compile-time null check for a runtime `UninitializedPropertyAccessException`, which is a worse failure mode than a nullable type with a clear error message.
- Kotlin has no checked exceptions, so wrapping Java APIs that declare `throws` needs no special handling — but still catch and log JDBC/`IOException`-style exceptions explicitly rather than letting them silently propagate into an event handler and get swallowed by Bukkit's plugin error handling.

## 7. Worked example (Kotlin translation of the `/heal` plugin)

Same behavior as the Java version in the main reference: `/heal <player>` with a config-driven message and PDC-backed cooldown.

**`HealPlugin.kt`**
```kotlin
package io.github.yourname.healplugin

import com.mojang.brigadier.Command
import io.papermc.paper.command.brigadier.CommandSourceStack
import io.papermc.paper.command.brigadier.Commands
import io.papermc.paper.command.brigadier.argument.ArgumentTypes
import io.papermc.paper.command.brigadier.argument.resolvers.selector.PlayerSelectorArgumentResolver
import io.papermc.paper.plugin.lifecycle.event.types.LifecycleEvents
import net.kyori.adventure.text.minimessage.MiniMessage
import net.kyori.adventure.text.minimessage.tag.resolver.Placeholder
import org.bukkit.NamespacedKey
import org.bukkit.attribute.Attribute
import org.bukkit.persistence.PersistentDataType
import org.bukkit.plugin.java.JavaPlugin

class HealPlugin : JavaPlugin() {

    private lateinit var cooldownKey: NamespacedKey

    override fun onEnable() {
        saveDefaultConfig()
        cooldownKey = NamespacedKey(this, "heal-cooldown-expiry")

        lifecycleManager.registerEventHandler(LifecycleEvents.COMMANDS) { event ->
            event.registrar().register(
                Commands.literal("heal")
                    .then(
                        Commands.argument("target", ArgumentTypes.player())
                            .executes(::executeHeal)
                    )
                    .build(),
                "Heals a player (with cooldown)"
            )
        }
    }

    private fun executeHeal(ctx: com.mojang.brigadier.context.CommandContext<CommandSourceStack>): Int {
        val resolver = ctx.getArgument("target", PlayerSelectorArgumentResolver::class.java)
        val target = resolver.resolve(ctx.source)[0]

        val now = System.currentTimeMillis()
        val expiry = target.persistentDataContainer.get(cooldownKey, PersistentDataType.LONG)
        if (expiry != null && expiry > now) {
            ctx.source.sender.sendPlainMessage("That player is still on cooldown.")
            return Command.SINGLE_SUCCESS
        }

        target.health = target.getAttribute(Attribute.MAX_HEALTH)!!.value

        val cooldownMs = config.getInt("cooldown-seconds", 30) * 1000L
        target.persistentDataContainer.set(cooldownKey, PersistentDataType.LONG, now + cooldownMs)

        val message = MiniMessage.miniMessage().deserialize(
            config.getString("healed-message", "<green>You healed <target>!</green>")!!,
            Placeholder.unparsed("target", target.name)
        )
        ctx.source.sender.sendMessage(message)
        return Command.SINGLE_SUCCESS
    }
}
```

`paper-plugin.yml` and `config.yml` are identical to the Java version — only `main:` needs to point at the Kotlin class's fully-qualified name (Kotlin classes are ordinary JVM classes, so this needs no special syntax).
